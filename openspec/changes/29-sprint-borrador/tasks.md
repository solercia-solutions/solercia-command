# Tasks: 29 · Sprint borrador (creación con solo nombre + autonombre)

## Reconciliación aplicada (orquestador)

1. **Nombre de la ruta de sugerencia** — `design.md` (D2) llama al endpoint
   `GET /projects/{id}/sprints/next-name` con el schema `SprintNextName`,
   mientras que `specs/sprints/spec.md` (delta persistida, autoritativa) y la
   instrucción explícita del orquestador ("Fase 4 endpoint suggested-name")
   usan `suggested-name`. Este documento usa `GET
   /projects/{id}/sprints/suggested-name` y el schema `SprintSuggestedName`,
   conforme a `spec.md` y a la instrucción recibida; el nombre de `design.md`
   queda superado, sin reabrirse en `apply`.
2. **Código de error para "iniciar un sprint ya cerrado"** — `design.md` (D3)
   fija "422 si `closed`" sin nombrar un `code` explícito (solo nombra
   `sprint_missing_dates` y `sprint_already_started`). Este documento decide
   `code="sprint_already_closed"` con `status_code=422` en `/start` (mismo
   concepto que el 409 de `/close`, distinguido por el status code y el
   endpoint) para no inventar un tercer nombre sin necesidad; puede renombrarse
   en `apply` si el equipo prefiere otro.
3. **Guarda de fechas en PATCH directo** — el orquestador confirmó
   explícitamente que la guarda de fechas al fijar `status=active` aplica a
   CUALQUIER mecanismo de transición, incluido `PATCH /sprints/{id}` con
   `status=active` directo (no solo `POST /start`, que es lo único que dice la
   letra de `spec.md`). Este documento incluye tests RED explícitos para ese
   camino (3.6-3.8), no solo para el endpoint dedicado.
4. **Permisos** — el orquestador confirmó que los endpoints nuevos (`/start`,
   `suggested-name`) usan el mismo modelo de permisos que el resto del módulo
   `sprints`: solo `Depends(get_current_membership)`, cualquier rol, sin
   restricción nueva (ya verificado como hecho en `state.yaml` al escribir la
   spec).
5. **Sin migración** — confirmado por `proposal.md`/`design.md`/`state.yaml`:
   `draft` es un valor libre de `String(20)` validado en el servicio; el
   default de columna sigue `'active'`. Ninguna Fase de este documento toca
   Alembic.

Todas las Fases son **secuenciales**, no hay paralelismo real entre ellas:
Fase 2 (creación) reutiliza la función pura de Fase 1; Fase 3 (`/start` +
guarda) reordena el `update_sprint` que Fase 2 ya tocó; Fase 4
(`suggested-name`) reutiliza `repo.last_for_project` + `next_sprint_name` de
Fases 1-2; Fase 5 (frontend) consume los tres endpoints de Fases 2-4 a la vez.

## Risks

- **Reordenar `update_sprint`** (3.9): aplicar los campos de fecha/nombre antes de validar `status` es un cambio de orden de ejecución dentro del mismo método; el riesgo es bajo porque no hay `await`/commit entre medio (solo `setattr` en memoria), pero cualquier lógica futura que dependiera del orden anterior debe revisarse contra este documento.
- **Código `sprint_already_closed` con dos significados** (Reconciliación #2): el mismo `code` se usa hoy en `close_sprint` (409, "ya está cerrado, no se puede volver a cerrar") y se reutiliza en `start_sprint` (422, "está cerrado, no se puede iniciar"). Distinguibles por `status_code` y por el endpoint, pero un cliente que solo mire `code` sin `status` podría confundir ambos casos; si esto molesta en `apply`, renombrar a un `code` distinto es un cambio de una línea.
- **Reactivar un sprint `closed` vía `PATCH status=active`** (botón "Reactivar" existente en la UI, línea 1462-1467 de `project-workspace.component.ts`) ahora también pasa por la guarda de fechas de 3.9; en la práctica no debería romper nada porque un sprint `closed` casi siempre tenía ambas fechas al haber sido `active` antes, pero no hay ningún test explícito en este documento para "reactivar un `closed` que además quedó sin fechas" (caso de borde no cubierto por la spec ni por el proposal — se puede agregar en `apply` si aparece).
- **Sin test runner de frontend**: `frontend/package.json` solo define `build`/`lint`/`watch`, no `test`; la Fase 5 se verifica exclusivamente con `npm run build` (mismo patrón que el cambio 34), sin cobertura automatizada de UI para el flujo nuevo.
- **Carrera entre "faltan fechas" en el cliente y en el servidor**: el botón "Iniciar sprint" se deshabilita en el cliente cuando falta una fecha (5.6), pero el servidor sigue siendo la fuente de verdad (3.9/3.10); si dos pestañas del mismo usuario editan el mismo sprint, el 422 del servidor debe seguir manejándose aunque el botón normalmente esté deshabilitado.
